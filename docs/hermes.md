# Hermes WebUI NixOS Module
This module packages the Hermes WebUI stack as a reproducible NixOS service set built around rootless Podman containers.
It is designed to run these components together:
* `hermes-agent`
* `hermes-webui`
* `hermes-dashboard` when enabled
* `caddy` when enabled
The module lives in [`hermes.nix`](../src/roles/nixos/files/etc/nixos/modules/hermes.nix) and exposes a single NixOS option set at `services.hermes-webui`.
## What The Module Does
* Creates a dedicated system user and group for the Podman runtime when `rootless = true`
* Creates the shared OCI network and named volumes
* Writes Hermes model configuration into the persistent `hermes-home` volume
* Copies a secret environment file into that same persistent volume so Hermes can read API keys at runtime
* Runs Caddy in front of Hermes WebUI and publishes only the Caddy port
## Runtime Layout
The stack uses these persistent objects by default:
* Network: `hermes-net`
* Config/state volume: `hermes-home`
* Agent source volume: `hermes-agent-src`
* Host workspace: `/var/lib/hermes-webui/workspace`
The main files end up here inside the `hermes-home` volume:
* `config.yaml`
* `.env`
Those files are generated by `hermes-webui-oci-setup.service` before the containers start.
## Secrets
Use `services.hermes-webui.environmentFile` for secrets such as:
```
OPENROUTER_API_KEY=sk-or-v1-...
HERMES_DEFAULT_MODEL=qwen/qwen3.6-flash
```
The module copies that file into the persistent Hermes home volume as `.env` and makes it readable by the Hermes container user. The file is not written into the Nix store.
The module also reads `HERMES_DEFAULT_MODEL` from that file when present and uses it to populate `config.yaml`. If the variable is absent, the fallback default is:
```
qwen/qwen3.6-flash
```
The generated WebUI runtime environment is kept in sync with the same resolved model so the browser picker starts on the same default instead of the WebUI image's provider fallback.
The provider and base URL are written as:
* Provider: `openrouter`
* Base URL: `https://openrouter.ai/api/v1`
### GitHub App credentials
Ansible renders `src/roles/secrets/templates/hermes-webui.env.j2` into the existing
`hermes_webui_env.age` secret. NixOS passes its decrypted runtime file to the
agent, WebUI, and dashboard, and copies it into the shared Hermes `.env`.
No credentials belong in Nix expressions or the Nix store.

| Ansible Vault key (`src/secrets.yml`) | Container environment variable |
| --- | --- |
| `hermes_github_token` (optional) | `GH_TOKEN` |
| `hermes_github_app_id` | `GITHUB_APP_ID` |
| `hermes_github_client_id` | `GITHUB_APP_CLIENT_ID` |
| `hermes_github_client_secret` | `GITHUB_APP_CLIENT_SECRET` |
| `hermes_github_private_key` | `GITHUB_APP_PRIVATE_KEY` |
| `hermes_github_installation_id` (optional) | `GITHUB_APP_INSTALLATION_ID` |

Unset or empty GitHub fields are omitted. Multiline PEM keys are encoded with
literal `\n` sequences so Podman receives one environment entry; the
[GitHub App plugin](https://hermes-agent.nousresearch.com/docs/plugins/github_app)
decodes these back into newlines. Client credentials are made available for
OAuth consumers; the documented plugin uses the App ID, private key, and
installation ID for installation authentication, not the OAuth client secret.

Credential injection does **not** install or enable a GitHub plugin. The documented
plugin additionally needs the App's installation ID (not its App ID or client ID);
add `hermes_github_installation_id` to the vault if using that plugin.

Deploy through the existing targeted automation:
```bash
./scripts/play.sh --limit habiki --tags hermes-runtime
```
After secret rotation, restart the setup unit and the Hermes app containers as
noted below; the copied `.env` must be refreshed as well as container environments.

### GitHub CLI inside both agent runtimes

The gateway agent and WebUI receive the same read-only mount at `/usr/local/bin/gh` from
`services.hermes-webui.githubCliPackage`. The default is the static nixpkgs
GitHub CLI payload, without its Nix-store shell wrapper. The build rejects a
binary requiring a dynamic loader. Only this executable is mounted, not the
host Nix store; no startup package installation or image modification occurs.
The current channel provides version 2.102.0, matching the latest GitHub release
checked for this change. Nix verifies the source and vendor hashes.

The focused deployment requires `age` on the controller's PATH; a temporary
`nix-shell -p age` provides it without modifying host package configuration.

CLI availability does **not** authenticate it. GitHub App fields are not `gh`
credentials, and the CLI does not mint an installation token automatically.
If needed, explicitly add `hermes_github_token` to encrypted `src/secrets.yml`;
the existing environment template maps it to `GH_TOKEN`. Use a least-privilege,
short-lived credential. Omit it to leave CLI authentication unconfigured.
Never put a token in `extraEnvironment`, a Nix expression, an image, or logs.

After deployment, `sudo -n podman exec hermes-agent gh --version` and
`sudo -n podman exec hermes-webui gh --version` must succeed.
The focused play also tests the CLI's normal unauthenticated error with token
variables removed and an isolated config path; it does not require or expose
actual GitHub credentials. It performs these checks in **both** containers:
WebUI imports and constructs its own `AIAgent` for chats, so gateway-only
installation would not cover browser-driven tool execution.

## Container Model
The module is set up for rootless Podman by default:
* Service user: `hermes-webui`
* Service group: `hermes-webui`
* Service UID/GID: `989`
* Container UID/GID: `1000:1000`
That split keeps the host service account separate from the user identity Hermes expects inside its containers.
The containers do not need sudo access or membership in any privileged host group.
## Port Exposure
The recommended setup is to expose only Caddy on the host and keep the app containers private on the internal Podman network.
Habiki uses **host Caddy**, `enableCaddy = false`, and
`caddyListenAddress = "127.0.0.1"`. Its WebUI backend is published only on host
loopback at `8787`; it is not directly reachable from the network. The agent
publishes no port. Preserve this binding: the module's optional Caddy container
is only a reverse proxy and does not itself implement Authentik access control.

For deployments using the optional Caddy container (`enableCaddy = true`), the
WebUI has no published port; only that proxy's chosen port is published. Do not
expose that proxy without a separate authentication boundary.
## Key Options
* `enable`: turn the stack on
* `backend`: `podman` or `docker`
* `rootless`: run containers as the dedicated service user
* `user` / `group`: host account names for the Podman service user
* `environmentFile`: secret env file containing API keys and runtime secrets
* `defaultModel`: fallback Hermes model
* `defaultModelEnvVar`: env var used to override the model from the secret file
* `inferenceProvider`: written into `config.yaml`
* `baseUrl`: provider URL written into `config.yaml`
* `caddyHostPort`: published host port for the proxy
* `webuiPort`: WebUI container port, default `8787`
* `gatewayPort`: Hermes gateway port, default `8642`
* `dashboardPort`: Hermes dashboard port, default `9119`
## Operational Notes
* `hermes-webui-oci-setup.service` is responsible for creating the network, volumes, and generated config files.
* `podman-hermes-webui.service` depends on the setup unit and the agent container.
* `podman-hermes-caddy.service` depends on the WebUI container.
* If you change the secret file, restart the setup unit and then restart the Hermes containers so they reload the copied `.env`.
## Example NixOS Configuration
```
{ services.hermes-webui = { enable = true; rootless = true; environmentFile = "/run/secrets/hermes-webui.env"; caddyHostPort = 8787; defaultModel = "qwen/qwen3.6-flash"; inferenceProvider = "openrouter"; baseUrl = "https://openrouter.ai/api/v1"; };
}
```
## Authentik-only Browser Access

On Habiki, host Caddy requires Authentik for every public WebUI route and passes
`X-Authentik-Username` to the WebUI. The existing trusted-proxy-related environment
settings are retained, but runtime inspection of the pinned image reports native
trusted-header authentication disabled. Do not rely on those settings as an
additional access control: Authentik at Caddy is the enforced browser boundary.
`HERMES_WEBUI_PASSWORD` is absent from both the vault-rendered environment and
Habiki's non-secret environment overrides; it is not set to an empty string.
Authenticated users should not receive a second Hermes password prompt.

The pinned image can also read a password hash from persisted `settings.json`.
Habiki had no persisted hash during preflight. If another deployment has one,
omitting the variable alone will not disable its password; resolve that through
managed migration before claiming passwordless access. Do not wipe shared state.

## Security Model
The module is intended to keep the Hermes containers unprivileged:
* dedicated host user and group
* no sudo access
* no extra host group membership
* secret material injected through a root-owned env file
* all app containers isolated on a private Podman network
The main host-level exposure is the chosen Caddy port.

## Focused Runtime Deployment and Rollback

Use `./scripts/play.sh --limit habiki --tags hermes-runtime`. This guarded path:

- Renders only the Hermes environment from Ansible Vault and encrypts it for the
  existing agenix recipients. Plaintext is passed on stdin, not written to disk;
  secret tasks use `no_log` and the encrypted file is replaced atomically.
- Copies only the Hermes encrypted secret, Hermes module, existing Caddy routing
  files, and Habiki device configuration.
- Runs `nixos-rebuild switch` without channel updates or OpenTofu, refreshes the
  shared Hermes `.env`, and restarts only the agent and WebUI containers.
- Checks container services, the absent password variable, `gh --version` inside
  both agent runtimes, and normal CLI behavior without credentials.

Encryption intentionally refreshes the ciphertext on each non-check deployment.
Before activation, review remote `/etc/nixos` drift: copying the device/Caddy
configuration and a host-wide NixOS switch can activate unrelated existing changes.
The older `--tags hermes` path remains available but also updates channels,
refreshes unrelated secrets, restarts other containers, and applies OpenTofu.
Do not use it for this focused rollout.

After deployment, verify `/` redirects an unauthenticated browser to Authentik,
`/health` returns JSON `401` without a redirect, and an Authentik-authenticated
browser opens the WebUI without a Hermes password prompt. Confirm the backend
remains bound only to `127.0.0.1:8787` and the agent has no published port.

Rollback: restore the previous Hermes template, module and Habiki device
configuration (including the prior password configuration if required), then
rerun the focused deployment. Retain the previous NixOS generation as an
emergency activation fallback, but note it does not restore encrypted secrets
or the copied shared `.env`. Do not remove Authentik as a workaround.

Local checks (Python needs Jinja2 and PyYAML):

```bash
python3 -m unittest scripts.tests.test_hermes_github_environment scripts.tests.test_hermes_runtime scripts.tests.test_hermes_auth_deploy
python3 scripts/tests/check_hermes_runtime_images.py --gh /nix/store/REPLACE-with-built-package/bin/gh
```

The image check uses the module's digest-pinned WebUI, no network or persistent
state, and mounts only the supplied static executable read-only. Run offline
unit tests via the Bubblewrap launcher; the image check needs approved Podman
access. The smoke check also runs without `--gh` to test only WebUI behavior.

## Expired Authentik Sessions

The host Caddy site reads `modules/hermes-auth.caddy`. For `/api`, `/api/*`,
`/health`, and `/health/*`, an outpost authentication redirect is translated to
JSON `401` with `Cache-Control: no-store` and no `Location` header. Authenticated
requests still require Authentik approval. Other auth failures remain failures.
Browser navigation, including `/login`, retains the normal OAuth redirect.

The pinned WebUI already handles API `401` by navigating at top level to
`login?next=...`; no CSP widening, frontend injection, image upgrade, or longer
session lifetime is needed. SSE reconnect handshakes receive `401` too; ordinary
API polling drives reauthentication. An already-established stream is not revoked
by these proxy rules.

### Proxy-only Deployment

```bash
./scripts/play.sh --limit habiki --tags hermes-auth
```

This focused play copies only `caddy.nix` and `hermes-auth.caddy`, then runs
`nixos-rebuild switch` and verifies Caddy. It does not update channels, refresh
secrets, apply OpenTofu, or blanket-restart containers. Other pending changes
already present in `/etc/nixos` can still be activated by a rebuild; inspect host
configuration drift before deployment. The normal full Hermes deployment remains
available for stack or provider changes.

After deployment, make no-cookie requests without following redirects:

- `/api/projects`, `/api/sessions/events`, `/api/settings`, `/api/crons/recent`,
  and `/health`: expect `401`, JSON, `no-store`, and no `Location`.
- `/` and `/login`: expect the usual `302` to Authentik.
- An authenticated tab should navigate to login on its next API poll after
  expiry; verify this in-browser when validating a future WebUI image update.

Roll back by reverting the Caddy routing changes and rerunning the focused play
(or deploy the previous `caddy.nix`, which does not read the new fragment). Do not
work around expiry by bypassing Authentik or allowing the identity origin in CSP.
